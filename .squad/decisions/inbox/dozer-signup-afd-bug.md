## 2026-08-26: Issue #84 sign-up via custom domain / AFD investigation

- **Summary:** Repo IaC does define an Azure Front Door profile for the Entra custom URL domain, but the module is minimal: one endpoint, one origin group, one origin, and one catch-all route. There are **no AFD rule sets, no rewrite actions, no redirect actions, and no cache configuration** in `infra/modules/frontDoor.bicep`.
- **Evidence against AFD query stripping:** The deployed storefront still emits an authorize redirect containing `prompt=create` for `/SignIn?handler=SignUpLink`, so the app-to-AFD hop preserves the sign-up intent.
- **Most likely root cause:** The deployment config globally points `AzureAd__Authority` (and `AzureAd__Instance`) at the **custom domain / AFD host** in `infra/main.bicep`, even though the checked-in storefront config uses the CIAM origin host and the app already has per-request host override logic for the CustomDomain demo (`src/storefront/Program.cs`, `src/storefront/Models/Demos/DemoDataList.cs`). This means every auth flow, including SignUpLink, is forced through the custom domain instead of using the default CIAM authority unless explicitly requested.
- **Confidence:** Medium. I did not inspect the live portal AFD config or Entra portal user flow, but code + live redirect traces show `prompt=create` leaving the app intact and no matching AFD rewrite/cache logic exists in repo IaC.
- **Recommendation:** Treat this as an **app/deployment auth-authority configuration issue first, not an AFD route/rules issue**. Change the storefront deployment to use the standard CIAM authority by default, and reserve the custom domain for the explicit CustomDomain demo/path override. Specifically review `infra/main.bicep` settings for `AzureAd__Authority` / `AzureAd__Instance` on the storefront app against the CIAM authority-only decision in `.squad/decisions.md` (2026-07-22T18:49:00Z).
- **Follow-up to confirm:** After changing the default storefront authority back to the CIAM origin host, re-test `/SignIn?handler=SignUpLink` and verify the first rendered auth experience is the intended sign-up/create-account flow. If behavior is unchanged, inspect the Entra user flow / custom URL domain service behavior next.

## 2026-08-26: Issue #84 fix implemented

- **Change made:** Updated `infra/main.bicep` so the shared `AzureAd__Authority` and `AzureAd__Instance` values now point to the tenant's canonical CIAM origin host (`entraOriginHost`) instead of the AFD-backed custom domain. The custom domain remains deployment-configured only through `Demos__CustomDomain`, which the storefront already uses to override the authorize host specifically for the `CustomDomain` demo flow.
- **Why this fixes #84:** The previous deployment forced all storefront auth challenges through the branded custom-domain path, including sign-up (`prompt=create`). That made the sign-up experience depend on the custom-domain behavior even when the user was not explicitly testing the CustomDomain scenario. Restoring the default authority to the CIAM origin host removes that global coupling.
- **Validation:** `az bicep lint --file infra/main.bicep` and `az bicep build --file infra/main.bicep --stdout` both completed successfully; lint emitted the existing `BCP318` warnings around optional `entraApps` outputs, but no new errors were introduced by this fix.
