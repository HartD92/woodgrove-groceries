## 2026-08-26: Issue #91 default browser-visible auth host should use the Entra custom domain

- **Decision:** Keep the application's canonical Microsoft.Identity.Web authority/instance on the tenant CIAM origin host (`hlacustomer.ciamlogin.com`), but rewrite the outgoing browser-facing OpenID Connect authorize URL host to the Entra custom domain (`customers.hartlabs.info`) by default for every storefront auth challenge.
- **Why:** Re-investigation showed the issue was not Azure Front Door query-string stripping. `infra/modules/frontDoor.bicep` defines a minimal pass-through route with no rule sets, rewrites, redirects, or cache/query manipulation, and the current live `/SignIn?handler=SignUpLink` redirect still includes `prompt=create`. The actual regression after issue #84 was that only the special `CustomDomain` demo path swapped the host, so ordinary sign-in/sign-up flows still exposed the CIAM origin hostname in the address bar.
- **Implementation:** Added `AzureAd__CustomDomain` to storefront deployment config, extracted redirect mutation logic into `src/storefront/Models/Identity/AuthRedirectCustomizer.cs`, and applied it from `src/storefront/Program.cs` for all OIDC challenges. The helper preserves prompt/login_hint/domain_hint/ui_locales and extra query-string parameters while changing only the issuer host, so sign-up's `prompt=create` survives the default custom-domain behavior.
- **Validation:** Live metadata at `https://customers.hartlabs.info/{tenantId}/v2.0/.well-known/openid-configuration` resolves and returns custom-domain authorize/token endpoints. `az bicep build --file infra/main.bicep --stdout` passed with only the pre-existing `BCP318` warnings. Local .NET test execution remains blocked because this machine only has SDK 9.0.317 while the repository targets net10.0.
